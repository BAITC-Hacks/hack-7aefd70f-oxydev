# 02 · Спецификация решения

---

## 1. Продуктовая идея

Qadam AI встраивается **до интервью** (предварительный скоринг заявки), **внутри интервью** (подсказки интервьюеру) и **после** (черновик обратной связи кандидату). Ровно те три точки, которые назвал заказчик.

Один экран, три роли:

- **Кандидат** — присылает видеопрезентацию/эссе, при необходимости проходит уточняющий диалог, получает обратную связь о том, что развивать.
- **Интервьюер** — получает разбор по ATOLA с цитатами, подсказки, какие блоки копнуть, и единую шкалу.
- **Комиссия** — сравнивает кандидатов по одной шкале, видит обоснование каждого балла, переопределяет любое решение одним кликом.

## 2. Архитектура: гибрид LLM + обученная модель

Это центральное техническое решение, и его надо уметь защитить.

```
Ответ кандидата (текст / транскрипт видео)
        │
        ▼
┌─────────────────────────────────────────┐
│ Слой 1. ИЗВЛЕЧЕНИЕ (LLM)                │
│ Структурирует, не оценивает.            │
│ • разметка фрагментов по A/T/O/L/A      │
│ • извлечение поведенческих индикаторов  │
│ • извлечение конкретики: цифры, роли,   │
│   сроки, имена, глаголы 1-го лица       │
│ Выход: строгий JSON, только цитаты      │
└─────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────┐
│ Слой 2. ПРИЗНАКИ (детерминированно)     │
│ • покрытие ATOLA (5 булевых + доли)     │
│ • индекс конкретности                   │
│ • индекс «воды» и клише                 │
│ • соотношение «я» / «мы»                │
│ • дельта траектории (было → стало)      │
│ • совпадение с BARS-индикаторами        │
└─────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────┐
│ Слой 3. СКОРИНГ (обученная модель)      │
│ Классификатор уровня: слабо / норма /   │
│ высоко, по каждой компетенции.          │
│ Логрег или градиентный бустинг на       │
│ признаках слоя 2 + эмбеддинги.          │
│ Калиброванные вероятности.              │
└─────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────┐
│ Слой 4. ОБЪЯСНЕНИЕ                      │
│ • вклад каждого признака в балл         │
│ • цитата-якорь под каждый индикатор     │
│ • подсказки интервьюеру                 │
│ • черновик обратной связи кандидату     │
└─────────────────────────────────────────┘
```

**Почему так, а не «спросить GPT, дай балл»:**

1. Общее ТЗ GovTech, п. 10.3: решение, полностью состоящее из промптов к готовой LLM, не засчитывается как полноценное AI-решение. Здесь есть обученная модель с метриками.
2. Воспроизводимость: LLM недетерминированна, обученный классификатор на фиксированных признаках — да. Комиссия не может защищать балл, который меняется между запусками.
3. Объяснимость: вклад признака в балл считается честно, а не пересказывается моделью.
4. Стоимость и скорость: LLM вызывается один раз на ответ, дальше всё локально.

**Формулировка для питча:** «LLM у нас не судья, а стенографист. Судит обученная модель на признаках, которые можно предъявить.»

## 3. Модули

### M1. ATOLA-разбор (ядро)
Вход: текст ответа + идентификатор компетенции. Выход: покрытие пяти элементов, уровень по BARS с вероятностью, цитаты-якоря под каждый сработавший индикатор.

### M2. Детектор «воды» и социально желаемых ответов
Признаки: отсутствие Outcome и Application при наличии Action; доля абстрактных конструкций; отсутствие числовых и временных маркеров; клишированные обороты; «мы» без указания личного вклада.
Выход: флаг + конкретное уточнение из методологии («Что было вашим личным вкладом, а не команды?»).

### M3. Контрфактический аудит справедливости
Механика: берём ответ, генерируем его вариант с изменённым **только** фоновым признаком (регион, тип школы, язык оригинала, «отполированность» речи), содержание и факты сохраняем. Прогоняем оба через скоринг, меряем Δ.
Метрика: медиана и 95-й перцентиль |Δ| по каждому фоновому признаку. Целевой порог — Δ не превышает разницу между соседними уровнями шкалы.
Это то самое «проверяемо на данных» из их критериев.

### M4. Подсказки интервьюеру и калибровка
До интервью: список компетенций, где сигнал слабый или противоречивый, с готовыми уточняющими вопросами.
Калибровка: одна шкала для всех интервьюеров; отклонение оценки интервьюера от модели показывается не как «ошибка», а как повод свериться. Модель никогда не перезаписывает оценку человека.

### M5. Уточняющий диалог (возвращение голоса)
Триггер: низкая конкретность или признаки сгенерированного текста. Бот задаёт 2–3 вопроса о деталях собственной истории кандидата по ATOLA. Оценка пересчитывается по ответам.
Балл за «похоже на ИИ» **не снижается никогда**.

### M6. Панель комиссии
Список кандидатов, единая шкала, раскрытие обоснования, кнопка переопределения с обязательным полем «почему», журнал переопределений (материал для дообучения на этапе внедрения).

## 4. Данные

### 4.1 Синтетический корпус

Реальных данных не будет до октября. Генерируем из опубликованной рубрики.

Размерность: 9 компетенций × 3 уровня × ~40 вариаций = ~1080 ответов, плюс контрфактические пары.

**Правило генерации:** промпт на порождение содержит **только** формулировки индикаторов нужного уровня из BARS, без слов «слабо/сильно». Метка берётся из того, какой набор индикаторов был заложен. Так метка не является пересказом собственного суждения модели.

Обязательные вариации по каждому уровню:
- длина: короткий / средний / развёрнутый;
- стиль: разговорный, канцелярский, «отполированный», с ошибками;
- язык оригинала: русский, казахский, смешанный;
- контекст: город / село, сильная школа / обычная;
- домен истории: школа, семья, волонтёрство, работа, собственный проект, спорт;
- «шумовые»: высокий уровень содержания в плохой формулировке и наоборот — низкое содержание в отличной обёртке. **Это самые важные примеры**, они учат модель не путать красноречие с потенциалом.

**Контрфактические пары:** тот же содержательный ответ, изменён только фоновый признак. Минимум 150 пар.

### 4.2 Экспертная разметка (обязательна)

Автоматической метки недостаточно. Размечаешь вручную вслепую 80–100 ответов по трём уровням, без просмотра сгенерированной метки. Считаешь согласие: доля совпадений и квадратично-взвешенная каппа между тобой и генератором, и отдельно между тобой и моделью.

Это единственный кусок работы, который нельзя делегировать, и именно он даёт право говорить «валидация» на защите.

### 4.3 Приватность

Синтетика — не персональные данные, это плюс на слайде «Надёжность и приватность». В коде сразу предусмотреть: обезличивание на входе, отсутствие хранения сырых текстов дольше сессии, отсутствие любых фоновых признаков в модели, логирование только агрегатов.

## 5. Валидация

Заказчику нужна не точность, а защищаемость. Поэтому четыре группы метрик.

### 5.1 Согласованность с рубрикой
На отложенной выборке (не участвовавшей в обучении): accuracy по трём уровням, квадратично-взвешенная каппа, матрица ошибок. Отдельно — согласие с ручной разметкой.

### 5.2 Сравнение с baseline (10 баллов рубрики)
Три baseline, по возрастанию:
1. случайное присвоение уровня по априорному распределению;
2. длина ответа (проверяет, не меряем ли мы просто многословность — важный и честный тест);
3. LLM без рубрики: «оцени этого кандидата от 1 до 3».

Показываем, что наша модель лучше всех трёх, и особенно — что она не сводится к длине текста.

### 5.3 Устойчивость
- перефраз: содержание сохранено, формулировки изменены → балл не должен меняться;
- ИИ-полировка: тот же ответ, прогнанный через LLM «сделай красиво» → балл не должен расти;
- усечение: удаление Outcome и Application → балл должен падать (проверка, что модель реально читает структуру).

### 5.4 Fairness
Δ по контрфактическим парам, разбивка по каждому фоновому признаку, медиана и хвост. Одно число на слайд.

## 6. Стек

Осознанно скучный, чтобы всё время ушло в содержание.

- **Backend:** Python 3.11, FastAPI, Pydantic.
- **ML:** scikit-learn (логрег + градиентный бустинг), sentence-transformers для эмбеддингов, joblib.
- **LLM:** Anthropic API, строгий JSON-выход, температура 0, кэш ответов на диск (обязательно — иначе демо разорит и будет тормозить).
- **Хранение:** SQLite или JSON-файлы. Postgres на MVP не нужен.
- **Frontend:** Vite + React + TypeScript, минимум зависимостей.
- **Деплой:** Render или Fly.io, одним контейнером.

Запуск строго одной командой. В README — точная инструкция, зависимости, ограничения. Это 10 баллов рубрики за документацию, которые теряют почти все.

---

## 7. Что не делаем

Чтобы не растечься:
- никакой авторизации, ролей, мультиарендности;
- никакой обработки видео на MVP — работаем с транскриптом, отметив, что это следующий шаг;
- никакого собственного банка forced-choice вопросов: он закрыт до октября, и делать свою версию бессмысленно;
- никакого скрейпинга соцсетей — прямо запрещено п. 6.3;
- никакого автоматического отказа кандидату: система только приоритизирует.
