# Qadam AI: план от MVP к принимаемому решению

Дата аудита: 20 сентября 2026 года.

## 1. Что подтверждают материалы заказчика

Qadam AI должен быть **инструментом поддержки комиссии до интервью**, а не
автоматическим допуском или отказом. Система должна показать доказательства,
снизить разброс оценок интервьюеров и оставить финальное решение человеку.

Текущий MVP корректно проверяет эту гипотезу на одной компетенции —
«Лидерские способности»: извлекает ATOLA и цитаты, считает BARS-уровень,
показывает вклад признаков и контрфактическую проверку. Метрики относятся
только к синтетическому корпусу и не доказывают качество на кандидатах.

Исторические ответы кандидатов недоступны из-за отсутствия согласия на
передачу третьей стороне. Поэтому допустимый путь валидации:

1. полная методология по NDA;
2. вымышленные пограничные кейсы от методологов;
3. слепая независимая разметка этих кейсов;
4. затем — проспективный пилот с отдельным согласием и контролем комиссии.

## 2. Текущий статус относительно Definition of Done

| Область | Сейчас | Следующий проверяемый результат |
|---|---|---|
| Бизнес-роль | Зафиксирован human-in-the-loop | Согласовать точное место в процессе и полномочия оператора |
| Методология | 1 из 9 компетенций, публичный BARS | Получить закрытые рубрики, веса и правила по NDA |
| Данные | 140 синтетических ответов, 40 пар | Экспертный reference set, затем consented pilot |
| Качество | Baseline, class metrics, robustness, fairness | Agreement с 2–3 экспертами и метрики отдельно RU/KK |
| Объяснимость | Цитаты, ATOLA, вклад признаков | Экспертно подтвердить понятность и полезность |
| Приватность | API больше не кэширует ответы | Threat model, сроки удаления, шифрование, аудит доступа |
| Воспроизводимость | Локальный запуск + Docker | Чистый подъём другим инженером и runbook |
| Надёжность | Offline heuristic fallback | Таймауты, очередь ручной проверки, нагрузочные тесты |
| Доступ | В MVP нет пользователей и ролей | Operator / supervisor / admin, минимальные права |
| Аудит | Нет журнала решений | Версии модели/методологии, override и причина |
| Языки | UI русский; корпус смешанный | Полноценные RU/KK интерфейс и отдельная оценка качества |
| Интеграция | Standalone API | Форматы входа/выхода, sandbox, владелец системы |

## 3. Приоритетный backlog

### P0 — до следующего показа

- согласовать один основной Given/When/Then-сценарий и два исключения;
- добавить статус «нужна ручная проверка» вместо уверенного ответа при низкой
  уверенности, сбое извлечения или недостатке доказательств;
- показать версию модели/методологии и источник каждого результата;
- написать smoke/integration tests для четырёх endpoint;
- проверить чистый запуск через `docker compose up --build`;
- убрать и отозвать все ранее опубликованные API-ключи.

### P1 — после получения методологии

- реализовать оставшиеся компетенции по одной общей схеме;
- определить нескорируемые и чувствительные блоки вместе с методологом;
- создать экспертный reference set и измерить inter-rater agreement;
- выбрать пороги уверенности по стоимости ошибок, а не «на глаз»;
- добавить русский/казахский UI и отчёт метрик по каждому языку.

### P2 — закрытый пилот

- роли, аутентификация и журнал действий/переопределений;
- PostgreSQL и защищённое объектное хранилище с политикой удаления;
- импорт/экспорт в согласованном формате или интеграция с sandbox;
- мониторинг ошибок, latency, drift и доли ручной очереди;
- runbook, модель угроз, лицензии, резервное копирование и план поддержки.

## 4. Что не следует обещать сейчас

- готовность к приёму или обработке реальных кандидатов;
- подтверждённую точность на реальных данных;
- автоматическое выявление AI-текста как основание для снижения балла;
- полный профиль по 9 компетенциям до получения методологии;
- соответствие законодательству без отдельной юридической проверки;
- production-ready статус только на основании Docker и красивого интерфейса.

## 5. Архитектурные решения, которые уже можно защищать

- LLM извлекает структурированные факты и дословные цитаты, но не принимает
  решение о кандидате.
- Финальный уровень вычисляется воспроизводимо обученной моделью на явных
  признаках.
- Фоновые и социально-экономические признаки не входят в скоринг.
- Чувствительные блоки можно маршрутизировать человеку без автоматического
  балла.
- При отсутствии внешнего LLM система деградирует до локального режима, а не
  прекращает работу.
- Пользовательские ответы API не записываются в дисковый кэш.

## 6. Решения, которые должен подтвердить заказчик

1. Кто основной пользователь первой версии: интервьюер, оператор отбора или
   руководитель комиссии?
2. Где именно результат Qadam AI появляется в существующем процессе?
3. Может ли система только приоритизировать интервью или также предлагать
   «не приглашать», если решение всё равно подтверждает человек?
4. Какая ошибка дороже: пропустить сильного кандидата или отправить слабого на
   интервью? В каком соотношении?
5. Какие блоки из девяти разрешено автоматически оценивать, а какие — только
   подсвечивать человеку?
6. Какова единица входа: текст анкеты, транскрипт видео, запись интервью или их
   комбинация?
7. Нужен ли казахский интерфейс уже для пилота и допустимы ли смешанные ответы?
8. Где должны храниться данные, каков срок хранения и кто имеет право доступа?
9. Кто будет владельцем системы, методологии и обновления модели через год?
10. Какие форматы/API и тестовый контур реально доступны для интеграции?
